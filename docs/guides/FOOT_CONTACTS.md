# Step 3b: contact sensors on both feet

This step adds measurements of foot/ground collision events. It does not change
joint commands, the crouch calculation, actuator interfaces or tracking tolerances.
It does not validate how much weight either foot supports.

## Signal path

```
left_foot_collision  -> left_foot_contact  -> /biped/left_foot/contacts
right_foot_collision -> right_foot_contact -> /biped/right_foot/contacts
                                              |
                                       Gazebo-to-ROS bridge
                                              |
                                   ros_gz_interfaces/msg/Contacts
```

The sensors observe existing collisions. No extra links, geometry or mass are added.

## Files changed and why

Paths are relative to `src/my_robot_description` unless noted otherwise.

### New: urdf/components/foot_contacts.xacro

A reusable `foot_contact_sensor(side)` macro attaches one sensor to each foot:

```xml
<gazebo reference="${side}_foot">
  <sensor name="${side}_foot_contact" type="contact">
    <always_on>true</always_on>
    <contact>
      <collision>${side}_foot_collision</collision>
      <topic>/biped/${side}_foot/contacts</topic>
    </contact>
  </sensor>
</gazebo>
```

- `reference` selects the foot link.
- `type="contact"` observes collision events.
- `collision` selects the existing foot collision by its converted SDF name.
- `topic` is inside `contact` because Harmonic's Contact system reads it there.
- The macro is instantiated for `left` and `right`.

Unlike the IMU implementation, Harmonic's Contact system publishes when contacts
exist, at the physics update cadence; we do not claim a configurable 100 Hz stream.
The measured contact stream on this setup is approximately 1,000 Hz.

### Changed: urdf/components/leg.xacro

Before:

```xml
<collision>
```

The foot collision now has an explicit URDF name:

```xml
<collision name="${side}_foot">
```

The URDF-to-SDF converter appends `_collision`. Thus `left_foot` becomes
`left_foot_collision` in SDF, exactly matching the sensor reference and the
previous autogenerated name. Naming it `left_foot_collision` in URDF would produce
`left_foot_collision_collision` with our converter; the conversion check caught
that during implementation.

The collision shape, origin and dimensions are unchanged.

### Changed: urdf/my_biped.urdf.xacro

Adds the component to the complete model:

```xml
<xacro:include filename="components/foot_contacts.xacro"/>
```

### Changed: worlds/standing.sdf

Loads the world system that creates and updates the contact sensors:

```xml
<plugin filename="gz-sim-contact-system" name="gz::sim::systems::Contact" />
```

Defining a sensor on the model alone does not load this world system.

### Changed: my_robot_description/sensors.py

Adds `make_contact_bridge(side)`. Each side starts a separate named bridge using:

```python
f'{topic}@ros_gz_interfaces/msg/Contacts[gz.msgs.Contacts'
```

The `[` indicates Gazebo-to-ROS forwarding. The topics remain raw contact messages,
not Boolean support decisions. No frame override is applied: changing a frame label
would not transform contact positions, normals or wrenches.

### Changed: my_robot_description/startup.py

Constructs both bridges, starts them with the other simulator components and
monitors their processes under `left-contact-bridge` and `right-contact-bridge`.
Unexpected process exit stops launch. The separate checker confirms actual data
arrival; a running bridge process alone is not proof of valid measurements.

### Changed: package.xml

Declares direct runtime dependencies on `ros_gz_interfaces` for the contact message
and `rosgraph_msgs` for the checker/clock interface. Both were already installed.

### New: my_robot_description/contacts.py

`ground_contact_pairs(message, side)` identifies collisions between the selected
foot shape and the current world's named `ground_plane`. It accepts either collision
ordering, rejects missing names, and avoids calling wall contact or the opposite
foot's contact ground support. This is a small adapter we can later reuse when
building feedback logic.

### New: workspace scripts/checks/check_contacts.py

After a settling interval, the checker observes both ROS topics for five simulated
seconds. It checks advancing timestamps, correct collision pairs, sample freshness,
maximum received gaps, and ground evidence in at least 99% of received samples.
It also uses `/clock` and a wall-clock deadline so a missing stream or paused
simulation cannot result in an indefinite wait.

Its result means **fresh foot/ground collision evidence**, not measured load sharing.
The nominal 0.1 s freshness threshold is for this integration check and has not
been chosen as a balance-controller timing requirement.

### New tests and documentation

- `tests/test_contacts.py`: collision ordering, opposite foot, wall, similar names,
  empty messages and missing names.
- `tests/test_contact_model.py`: runs the actual URDF-to-SDF converter and checks
  both sensor references resolve to collisions on their own foot links.
- This guide, with links added to README and the architecture guide.

## Run and inspect

From the workspace root:

```bash
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install --packages-select my_robot_description
source install/setup.bash
export ROS_DOMAIN_ID=42
export GZ_PARTITION=biped_recovery
ros2 launch my_robot_description standing.launch.py gui:=true stance:=crouch
```

In a second terminal, source the same environment and set the same ROS domain.
Wait for `[biped:standing]`, then:

```bash
python3 scripts/checks/check_contacts.py
```

For the raw collision records:

```bash
ros2 topic echo /biped/left_foot/contacts --once
ros2 topic echo /biped/right_foot/contacts --once
```

These messages contain contact points, normals, penetration depths and possibly
wrenches as well as collision names. We only validate collision identity and
freshness here; do not interpret the wrench arrays as calibrated foot-force sensors.

## Missing messages are not a trustworthy false value

The Harmonic implementation publishes only when contacts exist. Silence may mean
no contact, paused simulation, sensor/bridge failure or communication loss. We do
not publish a latched `supported=true` value that could remain stale after liftoff.
A future balance node must handle freshness and unknown status explicitly.

An explicit empty fresh message contains no contact evidence, but the current
backend does not promise to send one when contact disappears. This milestone tests
positive ground contact while settled; liftoff and dynamic contact transitions
remain future experiments.

## Physical regression checks

The converted SDF model before/after was compared after removing only the two new
contact sensors. The remainder was identical, including collision names and geometry.
This confirms sensor integration did not silently change dimensions, mass or joints.
